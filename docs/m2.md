# M2: DNS-BERT + Isolation Forest baseline

Owner: Thierry · Backup: Yehan · Trello: "[Thierry] M2: DNS-BERT tokenizers + pre-training + Isolation Forest on CIC"

## What it does
- **DNS-BERT** (`models/m2_dnsbert.py`): BERT, 4 layers, hidden 256, 4 heads, max 64 tokens, MLM pre-training
  on **benign names only** (CIC benign + Tranco top sites). Score = pseudo-log-perplexity (mean masked-token NLL);
  higher = more suspicious. Scoring is batched: every masked copy of a query, and copies from many queries,
  go through one forward pass, and only masked positions hit the MLM head. Unique qnames are scored once.
- Also outputs `info_bits` per query, I(q) = -sum log2 P(t_i | rest) (proposal eq. 1), for leakage accumulation.
- **Tokenizers:** BPE (8k vocab, main) and character-level (ablation 1); both trained on benign names only.
  Case is kept (tunnel encodings are often mixed-case; benign names are lowercase).
- **Isolation Forest** (`models/iforest_baseline.py`): benign-only, on the **M1 feature set**
  (`models/m1_features.py`: per-query + per-host window features), with M1's CIC leakage guard. On CIC that leaves
  11 features: entropy, n_digits, n_upper, n_special, digit_ratio, resp_size, qlen_wire, h_qpm, h_uniq_ratio,
  h_ent_mean, h_ent_std. Pass `feature_cols` to pick other columns.
- **Threshold** (written to the results JSON as `threshold`): the latest 10% of benign training rows by time are held
  out and never trained on; the threshold is their 99th-percentile score (<= 1% FPR), so the eval module never picks
  it on the test set. Known limitation, fixed in Phase 2: on CIC these rows come almost entirely from one capture
  (`benign_heavy_3.pcap`), because "latest by time" is taken across the whole table, not per capture.

Both follow the contract interface: `train(train_df, cfg)`, `score(model, df)`, `save`, `load`.

## Run
```bash
pip install -r requirements-m2.txt
python -m parser cic --raw data/raw/cic --out data/processed/cic/queries.parquet
python contracts.py data/processed/cic/queries.parquet
python -m models.m2_run --model m2 --exp E2 --data data/processed/cic/queries.parquet \
    --tranco data/external/tranco.csv --ckpt-dir "<leakmate captures>/m2/ckpt_bpe_v2"
python -m models.m2_run --model m2 --exp E2 --tokenizer char --tag ablation1_char --data ...
python -m models.m2_run --model iforest --exp E2 --data data/processed/cic/queries.parquet
python -m pytest tests/test_m2.py -q

# Phase 2, everything in one command (M2 on a GPU; the Isolation Forest part runs on CPU in minutes):
python scripts/m2_phase2.py --build-testbed data/raw/testbed \
    --phase1-bpe "<leakmate captures>/m2/ckpt_bpe_v2/last" --phase1-char "<leakmate captures>/m2/ckpt_char_v2/last" \
    --iforest --skip-existing
python scripts/m2_phase2.py --iforest-only     # reproduces results/iforest*/ exactly (deterministic, seed 42)
```
Output: `results/<model>/<run>.json` in the contract format (`docs/contracts.md` section 3): scores,
labels, tools, src_hosts, session_ids, ts, threshold, info_bits (M2), train time, per-query latency (batch of 1),
config. One folder per model variant, so the eval module groups every variant of a run together:
`m2/`, `m2_hostavg/`, `m2_ablation1_char/` (character tokenizer, ablation 1), `m2_ablation1_char_hostavg/`,
`iforest/`, `iforest_hostavg/`; run names `E1`, `E2`, `E3_<tool>`, `E4_cic2testbed`, `E4_testbed2cic`. Splits: the table's `split` column if present, else time-based 70/30 on `ts`.
On Colab (team Colab Pro): `notebooks/m2_phase2_colab.ipynb` (Phase 2) and `notebooks/m2_dnsbert_colab.ipynb` (Phase 1) reads everything from the shared Drive folder
**"leakmate captures"** (add it to My Drive as a shortcut): CIC zips from `raw/cic/`; checkpoints in
`m2/ckpt_*_v2/` (resume after a disconnect); results and weights copied to `m2/results/` and `m2/weights/`.

Synthetic test data (`scripts/make_synthetic_sample.py`) is for code testing only, never for reported results.

## CIC-Bell-DNS-EXF-2021: what the raw data really looks like (read before using it)
Built with `python -m parser cic --raw data/raw/cic`.
Download the **PCAP** folder from the CIC site (registration needed); the CSVs have no query text.

- **snaplen = 96 bytes.** Every packet is cut at 96 bytes, so only ~40 characters of each query name survive.
  Benign names (median 14 chars) are intact; ~99.9% of exfiltration names are truncated and lose their
  attacker domain. `qname_truncated` flags this; `qlen_wire` keeps the true query size.
  -> On CIC, `len(qname)` is capped and is NOT the real query length.
- **qtype is lost for truncated queries** (it sits after the name; the table stores `UNKNOWN`). Using qtype on
  CIC leaks the label, and so do capped lengths and the lost domain; the IF baseline drops all of these via
  M1's leakage guard (`models/m1_features.py`).
- **Only one attack tool** (DNSExfiltrator, base64url chunks `<n>.<data>` after an `init.<base32>` query),
  from one host. Attack pcaps also hold ~0.3% normal Windows lookups; those are labelled benign.
- **Benign traffic is scripted top-site lookups** (`domains_*.txt`), so it overlaps heavily with Tranco.
  CIC is an easy benchmark (IF baseline already reaches ROC-AUC 1.0); generalisation must be shown on the
  testbed, in Experiments 3 (leave-one-tool-out) and 5 (low-and-slow).
- Split: per capture file, first 70% of queries by time = train, rest = test.

## Phase 1 results: Experiment 2 (CIC benchmark, RTX 4060)
> Superseded: Experiment 2 was rerun in Phase 2 with the per-capture threshold hold-out; `results/m2*/E2.json`
> now hold those numbers (see "Phase 2 results" below). This table is the Phase 1 run, kept for the record.
From `python -m eval.summarise`; all three use the validation threshold above.

| Model | F1 | FPR | ROC-AUC | Train time | Latency (batch of 1) |
|---|---|---|---|---|---|
| M2 DNS-BERT, BPE (Phase 1 run) | 0.9980 | 0.81% | 0.99998 | 71 s | 5.2 ms |
| M2 DNS-BERT, char, ablation 1 (Phase 1 run) | 0.9979 | 0.83% | 1.00000 | 85 s | 6.3 ms |
| Isolation Forest (Phase 1 run) | 0.9980 | 0.79% | 1.00000 | 0.7 s | 20.1 ms* |

- Trained on 246,202 unique benign names (CIC benign train split minus the held-out 10%, + Tranco top 200k);
  test = 113,078 queries. The selection rule picks M2 (BPE).
- Mean `info_bits`: benign ~37 bits, exfil ~465 (BPE) / ~315 (char) bits per query, even with exfil names
  truncated to ~40 chars by the CIC snaplen.
- As expected, CIC (one tool, unthrottled) is near-trivially separable; the informative comparisons are Experiments 3-5 (leave-one-tool-out, cross-dataset, low-and-slow).
- Latency was measured on an RTX 4060 (earlier T4 runs: 7.4 / 6.8 ms). The official latency table is re-run on
  one fixed machine for every model.
- \* The IF latency **excludes feature extraction**: the M1 features are computed once for the whole table before
  scoring (needed for the past-only host windows), so the 20 ms is sklearn overhead per call. A live detector
  would also pay the per-query feature cost.

## Phase 2 results: testbed (Experiments 1, 3, 4), Colab T4
From `python -m eval.summarise`. Threshold set on held-out benign (latest 10% of **each** capture) at 1% FPR,
using the eval module's tie-aware `eval.metrics.threshold_at_fpr`, so at most 1% of held-out benign is flagged (see the note on threshold ties below). `_hostavg` = per-host averaging: mean score of the same host's queries in the past 60 s.
Run with `notebooks/m2_phase2_colab.ipynb` (`scripts/m2_phase2.py`); testbed table built from the 60 captures in
"leakmate captures", 4 h upstream-side benign run left out (team decision): 111,724 benign, 113,837 tunnel queries.

**Experiment 1 (within-testbed)**: M2 = Phase 1 model + continued pre-training on testbed benign (8,196 unique names)

| Model | Recall | FPR | ROC-AUC | Latency (T4) |
|---|---|---|---|---|
| M2 BPE | 0.812 | 0.21% | 0.9959 | 6.6 ms |
| M2 char (ablation 1) | 0.937 | 0.19% | 0.9991 | 6.5 ms |
| M2 BPE + host averaging | 1.000 | 0.50% | 1.0000 | 6.6 ms |
| M2 char + host averaging | 1.000 | 0.03% | 1.0000 | 6.5 ms |
| Isolation Forest | 1.000 | 0.91% | 1.0000 | 19.5 ms* |

**Experiment 3 (leave-one-tool-out)**: recall on the unseen tool (M2 never trains on tunnels, so the E1 model is reused)

| Unseen tool | M2 BPE | M2 char | M2 + host averaging (both) | Isolation Forest |
|---|---|---|---|---|
| dns2tcp | 0.998 | 1.000 | 1.000 | 1.000 |
| dnscat2 | 0.404 | 0.655 | 1.000 | 1.000 |
| DNSExfiltrator | 1.000 | 1.000 | 1.000 | 1.000 |
| iodine | 0.748 | 1.000 | 1.000 | 1.000 |

**Experiment 4 (cross-dataset)**: ROC-AUC / FPR at the source dataset's threshold

| | M2 BPE | M2 char | Isolation Forest |
|---|---|---|---|
| CIC → testbed (the E2 model: CIC benign + Tranco) | 0.9824 / 13.3% | 0.9960 / 13.3% | 0.8155 / 99.95% |
| testbed → CIC (new model, testbed benign only, no Tranco) | 0.9864 / 91.0% | 1.0000 / 9.3% | 0.9999 / 6.8% |

**Findings**
- Per-host averaging is what makes M2 work on unseen tools: per query it misses most dnscat2 (40% BPE) and many iodine
  queries; averaged per host over 60 s it catches all four unseen tools at 0.03-0.5% FPR.
- Ablation 1: the character tokenizer beats BPE on the testbed (E1 recall 0.937 vs 0.812; dnscat2 0.655 vs 0.404),
  while they tied on CIC.
- Experiment 4: ranking transfers across datasets (ROC-AUC 0.98-1.00) but the threshold does not; a threshold set on
  one network's benign traffic gives 9-91% FPR on the other (13% CIC→testbed), and per-host thresholds transfer worst. Deployment needs
  the threshold re-set on the target network's own benign traffic. M2 transfers far better than the IF (0.98/0.996 vs 0.82).
- Limitations: testbed benign comes from only 2 hosts (per-host FPRs near 0 are optimistic); testbed tunnels are long
  and easy per query (IF reaches 0.993 ROC-AUC on per-query features alone). 
- Suffix check (`docs/suffix-ablation.md`): every testbed tunnel name ends in `tunnel.test` and no benign name does.
  Retrained with that zone hidden, BPE recall rises (E1 0.812 -> 0.890) at 0.83% FPR, and host averaging and the IF
  are unchanged. The character model drops (E1 0.937 -> 0.737; dns2tcp 1.000 -> 0.223, iodine 1.000 -> 0.746), so
  the ablation 1 finding above (character beats BPE on the testbed) comes from the suffix; quote its masked numbers.
- Threshold ties (testbed): one very common benign name gets exactly the 99th-percentile score (0.83% of benign test
  queries share it). The first runs set the threshold with `np.quantile`, which landed on that score, so under the
  eval module's `score >= threshold` rule the plain-M2 testbed FPR was 1.02-1.04% (E1, E3). All results were
  re-scored (`--rescore`, same saved models, no retraining) with `eval.metrics.threshold_at_fpr`, which steps past
  the tie: FPR 0.19-0.21%, recall unchanged (no tunnel query has that score). CIC (E2, E4) and host-averaged scores
  had no such tie and barely moved (<= 0.15 points). With this, plain M2 meets the < 1% FPR rule on the testbed.
  Which model is selected per experiment is in `results/selection.csv` (M3 BiLSTM for E1, E3 and E5).
- E4 CIC→testbed scores with the E2 model, whose threshold rows were held out per capture and never trained on.
  (An earlier run reused the Phase 1 model, which had trained on 85% of those rows: 11.0% / 18.7% FPR. Found in code
  review and rerun; ROC-AUC barely moved, 0.9805 → 0.9824 BPE, 0.9951 → 0.9960 char.) The Isolation Forest trains fresh
  on CIC with the per-capture rule, so it was never affected.

**Experiment 2 rerun (CIC benchmark)** with the same per-capture threshold rule as E1-E4 (new models, CIC benign +
Tranco 200k, 3 epochs, Colab T4). These replace the Phase 1 E2 files.

| Model | Recall | FPR | ROC-AUC | Latency (T4) |
|---|---|---|---|---|
| M2 BPE | 1.000 | 1.21% | 0.99998 | 6.3 ms |
| M2 char (ablation 1) | 1.000 | 1.14% | 1.00000 | 6.7 ms |
| M2 BPE + host averaging | 1.000 | 3.33% | 0.99886 | 6.3 ms |
| M2 char + host averaging | 1.000 | 3.36% | 0.99880 | 6.7 ms |

- Ranking is unchanged from Phase 1 (ROC-AUC 0.99998 / 1.0). FPR is slightly above 1% for every model: the Phase 1

- Per-host averaging does not help on CIC (one scripted benign host with an unusual rhythm), unlike the testbed.

## Phase 3 results (18 Nov): Experiment 5, ablation 2, error analysis
Everything below that reads query names is on the **masked** testbed table (`python -m parser.mask`: every registered
domain, including the lab's `tunnel.test` zone, becomes `masked.domain`; `docs/suffix-ablation.md`). Run with

### Experiment 5 (low-and-slow)
`python scripts/m2_e5.py --results <dir>`. M2 and the Isolation Forest train on benign only, and Experiment 5 only
drops tunnel rows from training, so the Experiment 5 model, validation rows and thresholds are the Experiment 1 ones:
the Experiment 5 results are Experiment 1's test set filtered to benign + the 457 slow tunnel queries
(throttle >= 5,000 ms: iodine 271, dnscat2 118, DNSExfiltrator 68; dns2tcp has no slow runs), with host averaging
recomputed on those rows. `tests/test_m2_e5.py` checks this equals a direct `m2_run --exp E5` run.

Recall (FP), original -> **masked**:

| Model | Recall | ROC-AUC | iodine | dnscat2 | DNSExfiltrator |
|---|---|---|---|---|---|
| M2 BPE | 0.425 (72) -> **0.573 (278)** | 0.985 -> 0.887 | 0.288 -> 0.284 | 0.407 -> 0.992 | 1.000 -> 1.000 |
| M2 char (ablation 1) | 0.891 (64) -> **0.567 (277)** | 0.998 -> 0.890 | 1.000 -> not broken out | 0.576 -> not broken out | 1.000 -> not broken out |
| M2 BPE + host averaging | 1.000 (168) -> **1.000 (65)** | 1.000 -> 1.000 | 1.000 | 1.000 | 1.000 |
| M2 char + host averaging | 1.000 (10) -> **1.000 (45)** | 1.000 -> 1.000 | 1.000 | 1.000 | 1.000 |
| Isolation Forest | 1.000 (306) -> **1.000 (293)** | 1.000 -> 0.999 | 1.000 | 1.000 | 1.000 |
| Isolation Forest + host averaging | 1.000 (0) -> **1.000 (0)** | 1.000 -> 1.000 | 1.000 | 1.000 | 1.000 |

- **Per query, M2 misses most slow iodine** (0.28 on both tables): a slow iodine session is mostly 22-character
  polling names (`pabip11a.masked.domain`), and no tunnel name of 30 characters or fewer is caught (error analysis).
- **Per-host averaging catches every slow tunnel**, at 0.13-0.19% FPR on the masked table. Even one query every
  5-30 s leaves enough high-scoring queries in the host's 60 s window to keep its average over the threshold.
- The character model's original 0.891 came from the suffix (masked 0.567, the same as BPE).

### Ablation 2: pseudo-perplexity vs supervised fine-tuning (masked table only)
`models/m2_supervised.py`, `python scripts/m2_ablation2.py --root data/processed_nozone --init-from <ckpt_bpe_v2>/last`.
The **same Phase 1 model** (CIC benign + Tranco, never saw the testbed) gets a 2-class head and is fine-tuned on the
labelled testbed training rows (benign + tunnels, 2 epochs, lr 5e-5, class-weighted). Score = logit margin; threshold
from held-out benign at 1% FPR, as for M2. A supervised model sees tunnel names, so it only runs masked; Experiment 3
trains a new model without the held-out tool. One seed per run; 37-54 s training per run, 3.8-5.2 ms per query (T4).

| Run | M2 (pseudo-perplexity) recall / FP / ROC-AUC | Supervised recall / FP / ROC-AUC | Supervised + host averaging recall / FP |
|---|---|---|---|
| Experiment 1 | 0.890 / 278 / 0.978 | **1.000** / 693 / 1.000 | 1.000 / 167 |
| Experiment 3, dns2tcp held out | 0.871 / 278 / 0.998 | **0.045** / 16,503 / **0.249** | 0.043 / 1,062 |
| Experiment 3, dnscat2 held out | 0.997 / 278 / 1.000 | 0.770 / 78 / 0.844 | 0.971 / 1,061 |
| Experiment 3, DNSExfiltrator held out | 1.000 / 278 / 1.000 | 1.000 / 79 / 1.000 | 1.000 / 618 |
| Experiment 3, iodine held out | 0.746 / 278 / 0.932 | 0.746 / 48 / 0.806 | 0.999 / 15 |
| Experiment 5 (low-and-slow) | 0.573 / 278 / 0.887 | **1.000** / 78 / 1.000 | 1.000 / 725 |

- **Labels win on tools the model was trained on** (Experiments 1 and 5: recall 1.0; the slow tools are in training at
  normal speed) and **lose on a tool it has not seen**. Held-out dns2tcp drops to ROC-AUC 0.25, worse than chance, so
  the model ranks dns2tcp below benign. A likely reason (not checked) is that it learned long encoded names = tunnel,
  and dns2tcp's names are short. M2's benign-only score has no such blind spot (0.998).
- The supervised threshold does not hold on test traffic: 2.1% FPR on Experiment 1 and 49% with dns2tcp held out,
  against 1% on the validation rows. We have one run per setting and did not investigate further; treat the dns2tcp
  FPR as unexplained.
- So for RQ2 (unseen tools) the benign-only design is the right one; supervision only helps for tools you already have
  captures of.

### Error analysis (masked table)
`python scripts/m2_error_analysis.py` joins each results JSON to its query names (refusing if the rows do not line up)
and lists false alarms and misses at the run's own threshold. Full tables:
`results_nozone/m2_errors_masked.md` and `results_nozone/m2_errors_ab2.md`.

**Missed tunnels are short names, not dictionary-word encodings.** M2 BPE, Experiment 1 (3,770 missed of 34,180):

| Name length (characters) | Tunnel rows | Missed | Recall |
|---|---|---|---|
| up to 30 | 10,512 | 3,750 | 0.643 |
| 31 to 60 | 524 | 20 | 0.962 |
| over 60 | 23,144 | 0 | 1.000 |

- 99.5% of misses are 30 characters or fewer: iodine polling names (`paayessa.masked.domain`, 22 characters; 2,748
  missed; BPE and character models miss exactly the same 2,748, and the supervised model also misses 2,748) and
  dns2tcp (`Af8O7g7zBA.masked.domain`, 24; 1,002).
  With 8 random characters there is too little name left to look unusual. The other 20 are dnscat2 handshake names
  (`3f7c0121b896df7f620d0201ce29e0b4f0.masked.domain`, 48 characters of hex, scored just under the threshold).
- None of the misses are word-like encodings; the card's guess does not hold on this data (no tool here encodes with
  dictionary words).
- Per-host averaging recovers every one of them (0 missed): each short name is averaged with the same host's other
  tunnel queries in the past 60 s.

**False alarms are CDN-style generated host names.** M2 BPE, Experiment 1, 278 FP:
- 277 are one name, `img-prod-cms-rt-microsoft-com.<domain>`, a Microsoft CDN host whose first label is a whole
  hostname with dots turned into hyphens (score 5.685, just over the 5.674 threshold). The other is
  `64fz52su2k65naslgjsi.<domain>`, a random 20-character label.
- With host averaging (65 FP, 30 distinct names) the false alarms are CloudFront distribution IDs
  (`d7umqicpi7263`, `d1le29qyzha1u4`, ...), S3 and Azure blob buckets (`spot-price.s3`, `80c9968334697b.blob.core`),
  and the bare masked domain itself (23). So the card's guess (CDN hashes) holds for the averaged detector.
- Masking costs M2 false positives (72 -> 278 per query). Likely reason (not checked): it also removes the benign
  registered domains (`microsoft.com`, `cloudfront.net`) that made these generated labels look familiar.
