# M1: XGBoost + Random Forest baseline + SHAP

Owner: Joshua Tan · Trello: "[Joshua] M1: XGBoost + Random Forest baseline + SHAP on CIC"

## What it does
- **M1** (`models/m1_xgb.py`): XGBoost on per-query + per-host features. Score = P(tunnel), higher = more
  suspicious. Early stopping on a time-based validation slice of the training data (last 15% of each capture
  file), driven by logloss so scores stay calibrated on easy data.
- **SHAP**: exact TreeSHAP from XGBoost (`pred_contribs=True`), so scoring needs no extra dependency.
  `m1_xgb.explain(model, df, top_k)` returns the top features behind each alert (for the dashboard / live
  detector). `m1_run` also writes a global summary (`results/m1/shap/<exp>_shap.json`) and beeswarm + bar plots.
- **Random Forest baseline** (`models/rf_baseline.py`): same features, `class_weight="balanced"`.
- **Features** (`models/m1_features.py`): one place decides the columns, so M1 and RF always see identical inputs.
  - per-query: `models/qname_features.py` (stopgap, same as the IF baseline) + `qlen_wire`
  - per-host: `models/host_features.py`, a past-only sliding window (default 60 s) per
    `<source_file>|<src_host>`, so captures that reuse an IP never share a window and no future rows leak in.
  - when the parser's feature table lands, pass `feature_cols` and these stopgaps are skipped.

## Shared contracts
M1 and RF follow [`docs/contracts.md`](contracts.md) v1.0.0:
- **Query table (section 1):** they read only the required columns plus the optional `qname_truncated`, `qlen_wire`
  and `source_file` when present. `score` never reads `label`, `tool`, `split` or `throttle`.
- **Model interface (section 2):** `train(train_df, cfg=None)`, `score(model, df)` (P(tunnel), higher = more
  suspicious), `save(model, path)`, `load(path)`.
- **Results file (section 3):** `m1_run` writes every required key plus `session_ids` and `ts` (required before
  Experiments 3 and 5), and checks the record with `contracts.validate` before saving, so an invalid file is never written.
  `--exp` accepts only `E1`–`E5` and `S`; directions or variants go in `--tag` (e.g. `--exp E4 --tag cic2testbed`).
  Extra keys (`feature_cols`, `dropped_cols`, `feature_importance`, `shap`, `contract_version`, …) are allowed.

## CIC leakage guard (read before training on CIC)
CIC was captured with snaplen = 96 B (see `docs/m2.md`). On truncated exfil rows some features describe the
capture cut, not the tunnel. When the table's `qname_truncated` column marks at least one row as truncated
(`scripts/cic_to_queries.py` output), M1 and RF drop these groups by default:

| Group | Columns | Why it leaks on CIC |
|---|---|---|
| `qtype` | `qtype_code`, `is_txt_null`, `h_txt_null_ratio` | qtype sits after the name, so it is missing on truncated rows |
| `capped_length` | `q_len`, `sub_len`, `longest_label`, `h_len_mean` | lengths pile up at the ~40-char cut |
| `lost_domain` | `n_labels`, `sub_entropy`, `h_parent_uniq` | with the attacker domain cut off, `<n>.<data>` looks like a bare 2-label domain, which inverts the real signal |

Kept on CIC: `entropy`, `n_digits`, `n_upper`, `n_special`, `digit_ratio`, `resp_size`, `qlen_wire` (true query
size), `h_qpm`, `h_uniq_ratio`, `h_ent_mean`, `h_ent_std`. M2's IF baseline drops only the `qtype` group; M1 is
supervised and exploits artefacts more readily, so it drops all three. The ablation
`--keep-cic-leaky [GROUP ...]` measures how much each artefact inflates scores.

On tables with no truncated rows (testbed, parser output, synthetic sample, or `qname_truncated` all False) nothing
is dropped. `qlen_wire` is estimated as
`len(qname) + 18` when a table has no wire size, so a CIC-trained model can still score testbed tables (Experiment 4, cross-dataset).

## Run
```bash
pip install -r requirements-m1.txt
python scripts/cic_to_queries.py --raw data/raw/cic --out data/processed/cic/queries.parquet
python contracts.py data/processed/cic/queries.parquet          # prints "ok" if the table follows the contract
python -m models.m1_run --model m1 --exp E2 --data data/processed/cic/queries.parquet --save-model models/weights/m1.joblib
python -m models.m1_run --model rf --exp E2 --data data/processed/cic/queries.parquet --save-model models/weights/rf.joblib

# ablations
python -m models.m1_run --model m1 --exp E2 --features query --tag ablation_query_only --data data/processed/cic/queries.parquet
python -m models.m1_run --model m1 --exp E2 --keep-cic-leaky --tag ablation_cic_leaky --data data/processed/cic/queries.parquet
python -m models.m1_run --model m1 --exp S --split shuffled --data data/processed/cic/queries.parquet

python contracts.py results/m1/*.json results/rf/*.json        # every results file should print "ok"
python -m pytest tests/test_m1.py -q
```
On Colab: `notebooks/m1_xgb_colab.ipynb` (CPU runtime is enough; reads the CIC zips from Drive).

Output: `results/<m1|rf>/<exp>[_<tag>].json` in the shared results format (scores, labels, tools, src_hosts,
session_ids, ts, train time, per-query latency) plus `feature_cols`, `dropped_cols`, `feature_importance`, and for M1
`best_iteration` and the SHAP summary path. Latency is one raw query scored on its own (features + model),
batch of 1. A live detector keeps per-host window state between queries; scoring a lone row computes the
window from that row only, which is fine for timing.

## Phase 1 results: Experiment 2 (CIC benchmark)
Sanity numbers from `m1_run` (Windows laptop, CPU). The shared eval module produces the official metrics from
`results/*/E2*.json`. CIC table: 18 pcaps, 376,897 queries (251,564 exfil); train 263,819 / test 113,078.

| Model | ROC-AUC | Features | Train time | Latency (batch of 1) | Top-3 features |
|---|---|---|---|---|---|
| M1 XGBoost (`results/m1/E2.json`) | 1.0000 | 11 | 1.3 s | 13.56 ms | n_upper, qlen_wire, entropy (mean \|SHAP\|) |
| RF baseline (`results/rf/E2.json`) | 1.0000 | 11 | 6.6 s | 29.21 ms | n_upper, qlen_wire, entropy (impurity) |
| M1, artefacts kept (`results/m1/E2_ablation_cic_leaky.json`) | 1.0000 | 21 | 1.6 s | 14.31 ms | n_upper, qlen_wire, longest_label (gain) |
| M1, query features only (`results/m1/E2_ablation_query_only.json`) | 1.0000 | 7 | 1.5 s | 9.18 ms | n_upper, qlen_wire, entropy (gain) |
| M1, shuffled split (`results/m1/S.json`) | 1.0000 | 11 | 1.5 s | 13.49 ms | n_upper, qlen_wire, entropy (gain) |

Findings
- One feature dominates: `n_upper` has mean |SHAP| 7.99 (log-odds), then `qlen_wire` 2.36, `entropy` 0.46 and
  `resp_size` 0.12; host features are ~0. DNSExfiltrator's base64url payload is mixed-case while benign
  names are lowercase, so CIC is close to separable on that one feature. This may not transfer: lowercase
  encodings (hex, base32) would not trigger it, and resolvers that randomise case (0x20) could raise
  false positives. Experiment 4 (cross-dataset: CIC -> testbed with iodine, dnscat2, dns2tcp) tests this.
- With the artefacts kept, `longest_label` (capped-length group) enters the top 3 in place of `entropy`, so the
  model uses the snaplen cut as soon as it may. This supports dropping those groups by default.
- Every variant reaches ROC-AUC 1.0000 on CIC, so the artefact and shuffled-split ablations cannot show
  inflation here; they matter in Experiment 4 (cross-dataset), where scores are not saturated.
- Query-only M1 meets the < 10 ms target (9.18 ms). The per-host window adds ~4 ms per query, mostly pandas
  overhead for a single row; a live detector would update window state incrementally.
- RF matches M1's AUC but trains 5x slower and scores 2x slower, so M1 is preferred.
- `resp_size` may reflect how CIC's exfil server replies rather than tunnelling in general; check in Experiment 4 (cross-dataset).
