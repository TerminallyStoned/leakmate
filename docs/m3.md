# M3: character-level CNN + BiLSTM baseline

Owner: CY · Backup: HW · Trello: "[Neo] M3: E1, E2, E3, E4 (CNN + BiLSTM)" and "[Neo] M3: E5 + error analysis"

## What it does
- **Char-CNN** (`models/m3_cnn.py`): character embedding, Conv1D kernels 3/5/7, global max-pool, dense layer
  (about 0.36M parameters). Score = P(tunnel) for one query name.
- **Char-BiLSTM** (`models/m3_bilstm.py`): 1 layer x 128 units, mean + max pooling (about 0.23M parameters).
- Both are supervised and see **only the query name**: lower-cased, last 256 characters, 41-symbol vocabulary
  (`a-z 0-9 - _ .`; anything else, such as iodine's raw bytes, maps to one "unknown" symbol). No timing, size,
  record type or per-host features.
- Shared code in `models/m3_common.py`: encoding, training loop (class-weighted loss, early stopping), threshold,
  save/load. Both follow the contract interface.
- **Validation slice:** the latest 10% of training sessions, used for early stopping and the threshold only.
  If those sessions are all one class, the fallback takes the last 10% of rows by time **separately for benign and
  for each tool**. This matters on the testbed: benign and each tool were captured on different days, so the
  latest rows overall were tunnel traffic only (before the fix: 0 benign rows, dns2tcp only) and the threshold
  fell back to a default. With the fix, Experiment 1 validates on 7,821 benign and 7,967 tunnel rows from all
  four tools. CIC-trained runs never reach the fallback.
- **Threshold** (`pick_threshold`): chosen on the validation slice only. `lo` keeps validation false positives
  at or under 1%; `hi` still catches 99% of validation tunnels; when the classes are separated the threshold is
  the middle of the gap. It is written to the results JSON, so the eval module never picks it on test data.

## Run
```bash
python -m eval.run --model m3 --exp E1                 # trains and scores m3_cnn and m3_bilstm
python -m eval.run --model m3 --exp E3                 # all four held-out tools
python -m eval.run --model m3 --exp E4_cic2testbed     # also E4_testbed2cic, E2, E5
python contracts.py results/m3_*/*.json
python -m eval.summarise
```
Output: `results/m3_cnn/<run>.json` and `results/m3_bilstm/<run>.json` in the contract format; weights in
`artifacts/` (not committed). On Colab see `scripts/colab_m3.md`.

## Read this before quoting the testbed numbers
**Every tunnel name in the testbed ends in `tunnel.test`; no benign name does.** M3 reads the whole name, so the
suffix alone separates the classes. That is the likely reason E1, E3 and E5 are perfect, including on a tool the
model never saw: within the testbed the lowest tunnel score in any run is 0.979 and the highest benign score is
0.016. A slow tunnel still carries the suffix, so E5 says little about slowness for this model.

Experiment 4 is the evidence. CIC names are cut to about 41 characters by the capture and have lost their
domain (`docs/m2.md`). A testbed-trained CNN catches 2 of 75,323 of them, although CIC's tool is DNSExfiltrator,
which is in the testbed training set.

**Measured (18 Nov, `docs/suffix-ablation.md`):** retrained with the lab zone hidden, M3 keeps Experiment 1
(recall at least 0.998) but loses Experiment 3. A held-out dns2tcp is missed entirely, a held-out iodine is about
75% caught, and the CNN catches a third of dnscat2 and half of DNSExfiltrator. Quote the masked Experiment 3
numbers for unseen tools. **Experiment 4 remains the honest measure of what M3 learned.**

## Error analysis
Within the testbed (E1, E3, E5) there are no errors to analyse: 0 missed tunnels and 0 false alarms in all 12 runs.
All the errors are in Experiment 4.

- **Short names are invisible.** No tunnel name of 30 characters or fewer is caught by either model. That is all
  of dns2tcp and iodine's short control queries. CIC's tunnel names are all about 41 characters of dense
  base64, so a CIC-trained model has never seen a short tunnel name.
  - missed, dns2tcp: `+KACsgK3BA.dns2tcp.tunnel.test` (30 characters, score 0.0000)
  - missed, iodine: `paaygw1y.i.tunnel.test` (22 characters, score 0.0000)
- **Encoding matters less than length.** DNSExfiltrator is caught in base32 and base64 alike. iodine's raw-byte
  NULL records do worse than its Base32 TXT records (0.64 against 0.85 for the CNN), but those captures also
  have shorter names (median 102 against 253).
- **dnscat2 handshake-sized names split the two models.** At 31 to 60 characters the CNN catches 92% and the
  BiLSTM 0.4%.
  - `11ea015b0c4ee693a3e67200a2a29f1267.d.tunnel.test` (48 characters): CNN score 0.199, missed
  - `95d301447fbb717fc92323006472a065d4.d.tunnel.test` (48 characters): CNN 0.998 caught, BiLSTM 0.001 missed
- **Slow iodine is mostly missed.** On the 457 low-and-slow test rows: DNSExfiltrator 1.00 / 1.00, dnscat2
  1.00 / 0.89, iodine 0.28 / 0.28 (CNN / BiLSTM). This fits the length finding if a slow iodine session is mostly
  short keep-alive queries; we did not check the mix directly.
- **False alarms.** CNN: 38 rows (36 distinct names) of 33,519 benign, all hash-like CDN host names, for example
  `19747d839f8002b.cdn77.org` and `hmp3c74pjqpmpfb55dk7.storage.googleapis.com`. BiLSTM: none.

### Testbed -> CIC: what a testbed-trained model misses
All 75,323 CIC tunnel test names look like `637.e49YZhxpZX-7pgCXxHMdD7xELOdNlwlFlpydM`: 41 characters, cut by
the capture, no domain.

- **CNN:** catches 2 of 75,323. Median score 0.0 in all 12 attack files.
- **BiLSTM:** catches 43%, evenly across the 12 attack files (0.39 to 0.45), so it is not about the file type
  being exfiltrated. Two names of the same shape can score 0.0000 (`638.6xWRJAvScC8wkO5hjDtsEe_T5GunkfzlRjaNx`)
  and 1.0000 (`641.Trc6SiWKzWxP98I4NlefNVXQQw_eKwItxbq8N`).
- **False alarms.** BiLSTM: 72 rows (59 distinct names) of 37,755 benign, mostly short names in uncommon
  top-level domains, for example `downloadstatus.xyz`, `goldenpages.uz`, `honestppe.supply`. CNN: none.

## What this means for the report
- RQ2 (unseen tools): the original E3 numbers cannot answer it for M3, because the testbed suffix gives the
  answer away. Use the masked E3 numbers (`docs/suffix-ablation.md`). E4 CIC -> testbed is the other test:
  a model that has never seen our tools catches DNSExfiltrator and dnscat2 but none of dns2tcp.
- A name-only model cannot catch tunnels whose names are short. Catching those needs volume or timing features,
  which M1's per-host features have and M3 does not.
- The ROC-AUC in E4 (0.85 to 0.93) is well above the recall at the validation threshold, so part of the loss is
  a threshold that does not transfer between datasets, not only a model that cannot rank.

## Known limits
- The suffix shortcut above. E1 and E3 are rerun with the lab zone hidden (`docs/suffix-ablation.md`); E5 is not.
- GPU training is not bit-for-bit repeatable: rerunning the CIC-trained runs moved E4 CIC -> testbed recall by
  under 0.01.
- The fallback validation split takes rows, not whole sessions, so one session per tool can straddle the cut.
  It is training data either way; the test split is never touched.
